    Envoy¶

    Envoy from its admin statistics: downstream traffic per HTTP connection manager and listener, upstream clusters (requests, 5xx, latency, connections, retries, timeouts), cluster membership health and the server itself.

    Runbooks¶

    One per alert rule - the runbook the rule carries, or one generated from it - the text the board's Runbooks tab shows. A rule without a written runbook links to its page here, runbooks/<alert>/, which shows the same text.

    EnvoyHigh5xxRatio · warning · for 10m

    Meaning

    Envoy answers more than 5% of requests on {{ $labels.envoy_http_conn_manager_prefix }} with a 5xx.

    Downstream 5xx include upstream errors and Envoy's own 503s (no healthy upstream, circuit breaker overflow). The Upstream clusters and Health tabs tell which it is.

    It fires when the expression below holds for 10m.

    Impact

    Nothing is broken yet, and it will be if the trend holds. Look at it this working day.

    Diagnosis

    Run the alert expression and look at which series cross the threshold:

    sum by (cluster, job, envoy_http_conn_manager_prefix) (rate(envoy_http_downstream_rq_xx{envoy_response_code_class="5", envoy_http_conn_manager_prefix!="admin"}[5m])) / clamp_min(sum by (cluster, job, envoy_http_conn_manager_prefix) (rate(envoy_http_downstream_rq_total{envoy_http_conn_manager_prefix!="admin"}[5m])), 1e-9) > 0.050000000000000003

    Then open this board with the same selectors: the tab that carries those metrics shows how long the series has been where it is, and the restart and deploy annotations show whether a release or a restart lines up with the change.

    Mitigation

    • Confirm the target is the one you think it is: check the labels on the firing series.
    • Compare against the same series on a healthy peer; a single instance out of line is a different problem from every instance moving together.
    • If a deploy or restart lines up with the change, that is the first thing to undo.
    • If the threshold no longer matches how this service behaves, change the rule rather than living with a permanent alert.

    EnvoyUpstreamClusterUnhealthyMembers · warning · for 15m

    Meaning

    Envoy cluster {{ $labels.envoy_cluster_name }} has {{ $value }} unhealthy members.

    Health checks or outlier detection took hosts of the cluster out of rotation; the rest carry the load.

    It fires when the expression below holds for 15m.

    Impact

    Nothing is broken yet, and it will be if the trend holds. Look at it this working day.

    Diagnosis

    Run the alert expression and look at which series cross the threshold:

    max by (cluster, job, envoy_cluster_name) (envoy_cluster_membership_total) - max by (cluster, job, envoy_cluster_name) (envoy_cluster_membership_healthy) > 0

    Then open this board with the same selectors: the tab that carries those metrics shows how long the series has been where it is, and the restart and deploy annotations show whether a release or a restart lines up with the change.

    Mitigation

    • Confirm the target is the one you think it is: check the labels on the firing series.
    • Compare against the same series on a healthy peer; a single instance out of line is a different problem from every instance moving together.

    • If the threshold no longer matches how this service behaves, change the rule rather than living with a permanent alert.

    EnvoyUpstreamClusterNoHealthyMembers · critical · for 5m

    EnvoyDown · critical · for 5m

    Meaning

    Envoy {{ $labels.instance }} is down or draining.

    Either the admin endpoint cannot be scraped (up == 0) or the server reports it is not live (draining listeners, shutting down).

    It fires when the expression below holds for 5m.

    Impact

    Something users depend on is already broken or about to be. Treat it as an incident.

    Diagnosis

    Run the alert expression and look at which series cross the threshold:

    min by (cluster, job, instance) (envoy_server_live) == 0 or min by (cluster, job, instance) (up{job=~".*envoy.*"}) == 0

    Then open this board with the same selectors: the tab that carries those metrics shows how long the series has been where it is, and the restart and deploy annotations show whether a release or a restart lines up with the change.

    Mitigation

    • Confirm the target is the one you think it is: check the labels on the firing series.
    • Compare against the same series on a healthy peer; a single instance out of line is a different problem from every instance moving together.
    • If a deploy or restart lines up with the change, that is the first thing to undo.
    • If the threshold no longer matches how this service behaves, change the rule rather than living with a permanent alert.
